# NeForce Memory Pool 性能评估

## Windows

> 测试平台: i9-13980HX (8 P-core × 2 SMT + 16 E-core = 32 逻辑 CPU, 2419 MHz), Windows 11, MSVC 19.44 Release (`/O2 /arch:AVX2 /MD`)

### 单次分配 + 释放往返 (Pair/*)

|    请求 | CRT malloc/free | CRT operator new | NeForce memory_pool | 池 / malloc | 池 / operator new |
|--------:|----------------:|-----------------:|--------------------:|------------:|------------------:|
|    16 B |        25.80 ns |         26.10 ns |        **11.20 ns** |   **0.43×** |         **0.43×** |
|    64 B |        25.50 ns |         25.70 ns |        **11.30 ns** |   **0.44×** |         **0.44×** |
|   256 B |        25.30 ns |         25.80 ns |        **10.90 ns** |   **0.43×** |         **0.42×** |
|   1 KiB |        50.30 ns |         50.60 ns |        **21.70 ns** |   **0.43×** |         **0.43×** |
|   4 KiB |        50.70 ns |         50.00 ns |        **21.70 ns** |   **0.43×** |         **0.43×** |
|  16 KiB |        51.00 ns |         51.90 ns |        **22.50 ns** |   **0.44×** |         **0.43×** |
| 256 KiB |       153.00 ns |        153.00 ns |        **67.90 ns** |   **0.44×** |         **0.44×** |

- 16 B ~ 16 KiB 的往返延迟基本与请求尺寸无关（11.2 ~ 22.5 ns），符合"尺寸类 span + 线程本地缓存"的设计目标
- 相对 Windows CRT 堆快 **2.3 倍**：小对象由 25.5 ns 降到 11.3 ns，1 ~ 16 KiB 由 50 ns 级降到 21 ~ 23 ns
- 256 KiB 走大对象路径（独立映射区域 + 区域头部，无全池锁、无系统调用），67.9 ns，为 CRT 的 0.44×

### 尺寸类映射成本

|   请求 |    映射成本 |
|-------:|------------:|
|  1 KiB | **0.72 ns** |
|  4 KiB | **0.47 ns** |
| 12 KiB | **0.55 ns** |
| 16 KiB | **0.99 ns** |

- 映射由两级直接表承担
- 16 KiB 一行偏高，原因是该点附近跨越小对象上限，会多出一次不可预测分支

### 批量突发 (Batch/*)

一轮内 N 次分配 + N 次释放，归一化为每次分配或释放：

| 用例         | CRT malloc/free | CRT operator new | NeForce memory_pool | 池 / malloc |
|--------------|----------------:|-----------------:|--------------------:|------------:|
| 512 × 64 B   |        33.63 ns |         34.29 ns |         **8.81 ns** |   **0.26×** |
| 128 × 4096 B |       102.25 ns |         69.72 ns |        **10.98 ns** |   **0.11×** |

- 该模式下同时存在大量存活块，每次操作都可能跨批次与中央堆交互，因此绝对值高于单块往返
- 归还是按 span 分组成批拼接的：同一 span 的连续块只做一次空闲链拼接与一次计数更新，临界区长度与批量块数解耦
- 池在两处批量下的绝对成本（8.8 / 11.0 ns）与单块往返（11.3 / 21.7 ns）同量级，批量模式没有额外的操作开销

### 容器负载 (Container/*)

2000 条 `basic_string` 装入 `vector` 后整体析构：

| 负载               |        单元素成本 |
|--------------------|------------------:|
| 构造 + 增长 + 析构 | **34.02 ns/元素** |

- 元素多落在 16 ~ 128 B 尺寸类，每个元素的分配与释放合计约 34 ns
- 与 Linux 同类负载的 14.8 ns/元素之比为 2.3×，与单块往返的跨平台差距一致

- 4 KiB：池 8 线程 505.9 Mops，24 线程 673.5 Mops，每线程延迟由 12.0 ns 升到 35.6 ns，未出现类锁竞争悬崖
- CRT 堆在 16 线程起每线程延迟恶化到单线程的 2.2 ~ 2.8 倍（58 ~ 73 ns），池在同一窗口仍保有 2.0 ~ 2.4× 吞吐优势
- 全部线程窗口下池的总吞吐均高于 CRT，且随线程数持续增长（24 线程 788.7 / 673.5 Mops）

## Linux

> 测试平台: i9-13980HX (8 P-core / 16 逻辑 CPU + 16 E-core), Linux 6.17, Clang 20 Release (`-O3 -mavx2`)

### 单次分配 + 释放往返

|    请求 | glibc malloc/free | CRT operator new | NeForce memory_pool | 池 / malloc | 池 / operator new |
|--------:|------------------:|-----------------:|--------------------:|------------:|------------------:|
|    16 B |           7.63 ns |         10.34 ns |         **4.97 ns** |   **0.65×** |         **0.48×** |
|    64 B |           7.61 ns |          9.85 ns |         **4.96 ns** |   **0.65×** |         **0.50×** |
|   256 B |           7.59 ns |          9.87 ns |         **4.89 ns** |   **0.64×** |         **0.50×** |
|   1 KiB |           7.62 ns |          9.84 ns |         **4.97 ns** |   **0.65×** |         **0.51×** |
|   4 KiB |          17.94 ns |         22.20 ns |         **4.92 ns** |   **0.27×** |         **0.22×** |
|  16 KiB |          17.62 ns |         22.19 ns |         **4.87 ns** |   **0.28×** |         **0.22×** |
| 256 KiB |          17.40 ns |         21.68 ns |        **15.13 ns** |   **0.87×** |         **0.70×** |

- 16 B ~ 16 KiB 的往返延迟**与请求尺寸完全解耦**（4.87 ~ 4.97 ns，极差 2%）：命中线程缓存的分配与释放既不进入中央堆，也不产生系统调用
- 256 KiB 为 **0.87×**，载荷字节的判定让该档位留在每线程区域缓存内，且区域缓存按 32 KiB 起逐桶翻倍分桶，相邻尺寸不再互相挤占

### 批量突发 (一轮内 N 次分配 + N 次释放)

| 用例         | glibc malloc/free | CRT operator new | NeForce memory_pool | 池 / malloc |
|--------------|------------------:|-----------------:|--------------------:|------------:|
| 512 × 64 B   |    3.84 ns/次操作 |   5.82 ns/次操作 |  **2.97 ns/次操作** |   **0.77×** |
| 128 × 4096 B |    8.66 ns/次操作 |  10.80 ns/次操作 |  **4.73 ns/次操作** |   **0.54×** |

- 该模式同时存在大量存活块，每次操作都要跨批次与中央堆交互，因此绝对值高于单块往返

### 容器负载

2000 条 `basic_string` (长度 1 ~ 97 字节) 装入 `vector` 后整体析构:

| 实现                                       |        单元素成本 |
|--------------------------------------------|------------------:|
| CRT `operator new` (`std::allocator` 等价) |     14.79 ns/元素 |
| NeForce memory_pool (`pool_allocator`)     | **14.78 ns/元素** |
| 池 / operator new                          |         **1.00×** |

- 真实容器负载下每个元素的分配 + 释放（含字符串自身增长）合计约 14.8 ns，元素多落在 16 ~ 128 B 尺寸类
- 两种分配器在该负载上基本持平：开销由 `basic_string` 的构造与增长主导，分配器已不是瓶颈

### 内存驻留与回收

| 场景                                                        | 结果                                                                                                                          |
|-------------------------------------------------------------|-------------------------------------------------------------------------------------------------------------------------------|
| 20 万次 16 B 分配释放后                                     | 常驻 64 KiB (1 个 span), `active_bytes = 0`                                                                                   |
| 20 万次 4 KiB 分配释放后                                    | 常驻 128 KiB (2 个 span); 线程缓存按尺寸类保留一个批次的空闲块 (15 块 / 60 KiB), `flush_thread_cache()` 后 `active_bytes = 0` |
| 8 线程 × 2 万次混合尺寸 (1 B ~ 20 KB) churn 后              | 常驻 **2.5 MB**, `active_bytes = 0`, `verify() = true`                                                                        |
| `flush_thread_cache()` + `purge()`                          | `mapped_bytes` 归零, 驻留内存回落到基线                                                                                       |
| 20 轮 × 2 万块 4 KiB 批量 (存活工作集 80 MiB, 远超保留预算) | 映射与归还次数平衡 (25961 / 25922), 批量结束后常驻 2.5 MiB, 无单向增长                                                        |

- 空闲 span 按全池字节预算保留 (默认 2 MiB, 每个尺寸类至少 1 个), 突发负载的峰值工作集可复用而常驻上限可控
- 线程缓存持有的块在 `flush_thread_cache()` 或线程退出时归还; 只有归还后的 span 才会被 `purge()` 交还操作系统

### 多线程扩展性

测量方式: 16 个 E-core 窗口, 每线程每轮 2 万次 分配 + 释放, 5 轮 × 3 次重复取中位数。表中 ns/op 为**每线程单次分配 + 释放往返**。

请求 64 B:

| 线程 |  glibc 每线程 ns/op |  内存池 每线程 ns/op |  内存池 / glibc |  内存池总吞吐 |
|-----:|--------------------:|---------------------:|----------------:|--------------:|
|    1 |                7.69 |             **5.71** |       **0.75×** |       175 M/s |
|    2 |                8.47 |             **5.60** |       **0.66×** |       357 M/s |
|    4 |                9.13 |             **5.99** |       **0.66×** |       668 M/s |
|    8 |                8.96 |             **5.97** |       **0.67×** |  **1340 M/s** |
|   16 |                9.81 |             **7.68** |       **0.78×** |  **2083 M/s** |

请求 4 KiB:

| 线程 |  glibc 每线程 ns/op |  内存池 每线程 ns/op |  内存池 / glibc |  内存池总吞吐 |
|-----:|--------------------:|---------------------:|----------------:|--------------:|
|    1 |               31.62 |             **5.69** |       **0.18×** |       176 M/s |
|    2 |               27.64 |             **5.63** |       **0.20×** |       356 M/s |
|    4 |               29.05 |             **5.94** |       **0.20×** |       673 M/s |
|    8 |               29.47 |             **5.73** |       **0.19×** |  **1396 M/s** |
|   16 |               32.43 |             **7.58** |       **0.24×** |  **2112 M/s** |

- 每线程延迟在 1 ~ 8 线程上保持 5.6 ~ 6.0 ns（与单线程 P-core 的 4.9 ns 同量级），16 线程升到 7.6 ns，**没有出现类锁竞争悬崖**
- 总吞吐随线程数近似线性：64 B 由 175 M/s 增至 2083 M/s（16 倍线程 11.9 倍吞吐），4 KiB 由 176 M/s 增至 2112 M/s（12.0 倍）
- 4 KiB 上每操作为 glibc 的 0.18 ~ 0.24×：E-core 簇的共享带宽对 glibc 的大块路径影响远大于尺寸类 span 路径
- 64 B 上与 glibc 的差距稳定在 0.66 ~ 0.78×：即使到 16 线程，池的每操作成本仍明显低于 E-core 上的 tcache

#### 24 核窗口 (8 P-core + 16 E-core)

测量方式: 不限制进程 CPU，由基准按物理核绑定工作线程；每线程每轮 2 万次 分配 + 释放。

| 纯 E-core × 16       |          **7.68** |     2083 M/s | **0.78×** |           **7.58** |     2112 M/s |  **0.24×** |
| 混合 × 24 (8P + 16E) |          **8.56** | **2803 M/s** | **0.86×** |           **8.30** | **2892 M/s** |  **0.25×** |

| 工作线程 | 64 B 池 | 64 B glibc | 64 B 总吞吐 | 4 KiB 池 | 4 KiB glibc | 4 KiB 总吞吐 |
|---------:|--------:|-----------:|------------:|---------:|------------:|-------------:|
|        1 |    5.72 |       7.84 |     175 M/s |     5.68 |       37.26 |      176 M/s |
|        2 |    5.65 |       8.26 |     354 M/s |     5.56 |       32.64 |      360 M/s |
|        4 |    5.96 |       9.33 |     671 M/s |     5.97 |       31.07 |      670 M/s |

- 24 线程总吞吐 **2803 M 次操作/秒**（64 B）与 **2892 M 次操作/秒**（4 KiB），相对 8 个 P-core 提升到 2.10 / 2.18 倍
- 每线程延迟由 5.7 ns（1 线程）平滑升到 8.6 ns（24 线程），**未出现类锁竞争悬崖**
- 与 glibc 的比值在所有窗口中一致：64 B 为 0.66 ~ 0.86×，4 KiB 为 0.19 ~ 0.25×，即 24 核满负载下 4 KiB 仍保有约 4 倍的每操作优势
- 工作线程由基准固定到物理核（8 个 P-core 主线程优先，再依次使用 16 个 E-core），避免了调度器在 32 个逻辑 CPU 上迁移带来的缓存与 TLB 失效

## 跨平台对比

| 场景                  | Windows (MSVC) | Linux (Clang 20) | 说明                         |
|-----------------------|---------------:|-----------------:|------------------------------|
| 64 B 单次往返 · 池    |       11.30 ns |      **4.96 ns** | 平台绝对差距 2.3×            |
| 64 B 单次往返 · CRT   |       25.50 ns |      **7.61 ns** | ucrt 比 glibc tcache 慢 3.4× |
| 4 KiB 单次往返 · 池   |       21.70 ns |      **4.92 ns** |                              |
| 4 KiB 单次往返 · CRT  |       50.70 ns |     **17.94 ns** |                              |
| 256 KiB 单次往返 · 池 |       67.90 ns |     **15.13 ns** | 大对象路径                   |
| 容器负载              |   34.0 ns/元素 | **14.8 ns/元素** | 同一负载                     |
| 4 KiB 16 线程每线程   |       30.29 ns |      **7.58 ns** | Linux 为 16 E-core 窗口      |

- 池的相对优势在两个平台都成立，且 **Windows 上更明显**：对 CRT 为 0.43×（快 2.3 倍），Linux 上对 glibc tcache 为 0.65×（快 1.5 倍）
- 差异来自基线而非池：ucrt `malloc` 在 64 B 上比 glibc tcache 慢 3.4 倍，而池自身的绝对延迟只差 2.3 倍
- 绝对延迟的 2.3× 差距与移动端 SoC（2419 MHz）对桌面级 P-core 的频率/微架构差距一致

## 与工业级分配器对照

- Windows 上对 ucrt 快 2.3 倍；Linux 上对 glibc tcache 快 1.5 倍，4 ~ 16 KiB 上快 3.6 倍，批量模式快 1.3 ~ 1.9 倍
- jemalloc / tcmalloc / mimalloc 等工业级分配器的公开小对象往返数据与上表处于同一量级（数纳秒至数十纳秒，取决于尺寸与平台）；本项目未在相同环境复测，故不列具体数值
- 256 KiB 大对象路径的绝对成本（67.9 / 15.1 ns）明显高于小对象，但在 Linux 上已快于系统分配器

## 总结

- **单次往返 4.87 ~ 4.97 ns**，与请求尺寸完全解耦；为 Windows CRT 堆的 **0.43 ~ 0.44×**，为 Linux glibc tcache 的 **0.64 ~ 0.65×**（4 ~ 16 KiB 上为 0.27 ~ 0.28×），256 KiB 为 0.87×
- **批量模式 3.0 ~ 4.7 ns/次操作**（Windows 8.8 ~ 11.0 ns）；容器负载 14.8 ns/元素（Windows 34.0 ns/元素），与 `operator new` 持平
- **多线程**：24 线程窗口 64 B 达 2803 Mops、4 KiB 达 2892 Mops，每线程延迟 8.6 ns，未出现类锁竞争悬崖；16 个 E-core 窗口由 175 M/s 扩到 2083 M/s

## 可优化方向

| 方向                                                          | 预期收益                                                 | 复杂度 |
|---------------------------------------------------------------|----------------------------------------------------------|:------:|
| 归还路径按 span 头部取尺寸类，省掉发布/回收时对映射条目的写入 | 批量模式的登记成本再降一档，同时缩短大对象释放路径       |   中   |
| 大对象区域缓存按 16 KiB 粒度细分（当前 32 KiB 起翻倍）        | 相邻尺寸的大对象负载命中率再提升                         |   低   |
| 跨线程归还合并（多个线程对同一 span 的归还合并成一次拼接）    | 高并发 flush 场景的类锁进入次数下降                      |   中   |
| 大对象路径在区域头部内联归属信息                              | 256 KiB 往返继续下降，代价是失去"任意指针可安全判定归属" |   中   |
| 容器负载补充 `map` / `list` 节点形态的独立对照基线            | 容器结论覆盖更多节点形态                                 |   低   |
