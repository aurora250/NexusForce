# NeForce 虚拟线程性能评估

## Linux

> 测试平台: i9-13980HX (8 P-core / 16 逻辑 CPU + 16 E-core), Linux 7.0.0, Clang 20.1.2 Release (`-O3 -mavx2`)

### 任务创建与完成 (无挂起点)

一个任务体如果没有 `co_await`，`virtual_thread::start()` 会在调用线程上直接把它执行完：不进调度器队列，
只剩共享状态分配、协程帧分配、两次引用计数与一次完成发布。

| 用例                                              |    时间 | 说明                                    |
|---------------------------------------------------|--------:|-----------------------------------------|
| `virtual_thread::start()` + `get_result()` (void) | 43.7 ns | 含共享状态与协程帧两次堆分配            |
| `virtual_thread::start()` (不取结果)              | 42.4 ns | 去掉 `get_result()` 的"已完成"快路径    |
| `virtual_thread::start()` + `get_result()` (int)  | 43.2 ns | `aligned_buffer` 返回路径，与 void 持平 |
| 裸协程帧 (创建 + 两次 `resume` + 销毁)            | 10.6 ns | 无共享状态、无调度器，作为下限          |

- 任务外壳相对裸协程的固定开销约 **33 ns**：`task_shared_state` 的 `new`/`delete` 是主要来源
- 无人等待的任务完成时不加锁、不广播（只写一个原子标志），完成之后调用 `get_result()` 只剩一次原子读
- 返回 `int` 与返回 `void` 无差异，说明 `aligned_buffer` 结果存储不构成额外开销

### 调度往返 (`co_await virtual_thread::yield()`)

任务体只含一次 `yield`：帧进入无锁就绪队列、worker 被 FUTEX 唤醒后恢复、`final_suspend` 再唤醒调用
`get_result()` 的线程。这段延迟包含一次线程唤醒，因此明显高于上面的内联路径。

| Workers | 往返延迟 | 往返吞吐 |
|--------:|---------:|---------:|
|       1 |  3.07 µs |   656k/s |
|       2 |  3.56 µs |   619k/s |
|       4 |  3.80 µs |   560k/s |
|       8 |  4.32 µs |   548k/s |
|      16 |  3.91 µs |   614k/s |

- 往返延迟与 worker 数基本无关（3.1–4.3 µs），瓶颈是"把等待线程唤醒"，而不是调度器排队
- 单次往返里协程自身只占很小一部分：真正昂贵的是调用方线程的睡眠与唤醒

### 连续 yield 的边际成本 (4 workers)

同一个任务内连续 `co_await yield()`，用长链摊薄一次 `get_result()` 的等待成本。

| 每个任务的 yield 次数 |  总时间 | 每个 yield |
|----------------------:|--------:|-----------:|
|                     1 | 4.28 µs |    4.28 µs |
|                     8 | 4.59 µs |     574 ns |
|                    64 | 6.45 µs |     101 ns |
|                   512 | 23.6 µs |      46 ns |

- 摊薄后每次"重新入队 + 被恢复"约 **38 ns**：链上的入队发生在工作线程内部，不会再唤醒其它 worker
  （发起者下一轮循环自己取走），只剩无锁队列与两次原子计数的成本
- 与单次 `yield` 的 3–4 µs 对比可见：往返成本几乎全部来自**调用方线程的阻塞等待**

### 单生产者调度吞吐 (每个任务一次 yield，单线程提交并逐个等待)

| Workers | 1000 任务 | 10000 任务 | 单任务成本 |
|--------:|----------:|-----------:|-----------:|
|       1 |    265 µs |    3.13 ms |     265 ns |
|       4 |    616 µs |    6.52 ms |     652 ns |
|      16 |   1118 µs |   10.34 ms |    1034 ns |

- 单等待者串行负载下 worker 越多越慢：任务在提交线程等待期间被不同 worker 恢复，跨核唤醒与全局队列
  竞争都不再是"本地"操作
- 该基准衡量的是"一次只等一个任务"的延迟敏感负载；并行吞吐见下两节

### 多生产者提交 (8 workers, 每生产者 500 个任务)

| Producers | 提交耗时 | 提交/任务 | 提交速率 | 收尾排空 |
|----------:|---------:|----------:|---------:|---------:|
|         1 |   486 µs |   0.97 µs |  1.03M/s |  3.78 µs |
|         2 |   969 µs |   0.97 µs |  1.03M/s |  6.99 µs |
|         4 |  1.01 ms |   0.50 µs |  1.99M/s | 12.08 µs |
|         8 |   791 µs |   0.20 µs |  5.06M/s | 22.24 µs |

- 无锁队列把提交侧的互斥消掉，8 生产者提交 4000 个任务只用 791 µs（约 5M tasks/s）
- 任务在提交过程中就被 worker 取走执行，提交结束后的排空只有 4–22 µs

### 计算扩展 (256 个任务 × burn(50000)，串行参考 14.31 ms)

任务体先 `yield` 一次把自身交给 worker，再执行计算；否则 `start()` 会内联跑完，调度器不参与。

| Workers | makespan | 相对串行加速 | 效率 |
|--------:|---------:|-------------:|-----:|
|       1 | 14.43 ms |        0.99× |  99% |
|       2 |  7.46 ms |        1.92× |  96% |
|       4 |  3.87 ms |        3.71× |  93% |
|       8 |  2.09 ms |        6.85× |  86% |
|      16 |  1.24 ms |        11.6× |  73% |

- 8 worker 内接近线性（93%/86%）；16 worker 效率 73%，来自全局就绪队列与跨核唤醒
- 工作线程每次只取一个协程（不做批量抢占），长任务在 16 worker 下仍能均匀分摊

### `co_await` 子任务 (4 workers)

每次等待一个未完成的子任务要付出两次调度跳：子任务被 worker 恢复，以及子任务 `final_suspend()` 把父协程
的 continuation 重新入队。

| 深度 |  总时间 | 每次 await |
|-----:|--------:|-----------:|
|    1 | 4.16 µs |    4.16 µs |
|   32 | 9.26 µs |     289 ns |
|  256 | 43.2 µs |     169 ns |

扇出（父任务先启动全部子任务，再逐个 `co_await`）：

| 子任务数 |  总时间 | 每子任务 |
|---------:|--------:|---------:|
|        8 | 6.09 µs |   761 ns |
|       32 | 20.1 µs |   628 ns |
|      128 | 80.2 µs |   626 ns |

- 链式 await 的边际成本约 **153 ns**：continuation 的入队不再抢锁，且由完成者所在的工作线程直接取走
- 扇出把子任务一次性铺满队列，每个子任务摊到 **0.63 µs**（含跨 worker 唤醒）

### 定时挂起精度 (`co_await virtual_thread::sleep(ms)`, 4 workers)

|   目标 |      实际 | 平均偏差 | 同参数 `this_thread::sleep_for` 平均偏差 |
|-------:|----------:|---------:|-----------------------------------------:|
|   1 ms |   1.20 ms |   196 µs |                                    68 µs |
|  10 ms |  10.31 ms |   307 µs |                                   149 µs |
|  50 ms |  50.34 ms |   332 µs |                                        — |
| 200 ms | 200.34 ms |   336 µs |                                   158 µs |

- 调度器自身的额外偏差约 **130–180 µs**：定时器到期后 worker 还要把帧重新入队、再唤醒等待者
- 本机纯 `sleep_for(10 ms)` 自身偏差已有 149 µs（timer slack + 虚拟化），1 ms 级精度不应依赖 `sleep()`
- 长延时相对偏差很小：200 ms 上约 0.17%

### 空闲开销 (worker 全部停驻)

| Workers | 占单核 | 每 worker |
|--------:|-------:|----------:|
|       1 | 0.033% |    0.033% |
|       4 | 0.046% |    0.011% |
|      16 | 0.046% |    0.003% |

- 停驻 worker 阻塞在 FUTEX 上，没有自旋、没有周期性唤醒，空闲成本与 worker 数无关

### 基线对比

| 实现                               |       单次"交给别的线程并等它跑完" |
|------------------------------------|-----------------------------------:|
| `thread` 每任务建线程              |         16.1 µs（其中 CPU 8.6 µs） |
| 手写 mutex + condition_variable 池 | 3.23 / 4.14 / 3.56 µs (1/4/8 线程) |
| **NeForce `virtual_thread`**       |    **3.07–4.32 µs** (1–16 workers) |

- 与手写互斥池同一量级，多 worker 时略优；相对每任务建线程快约 **4–5×**
- 任务本身（无挂起）43.7 ns，是调度语义（结果存储、异常传播、`get_result()` 唤醒）的成本

## 可优化方向

| 方向                                                                         | 预期收益                                      | 复杂度 |
|------------------------------------------------------------------------------|-----------------------------------------------|:------:|
| 批量入队时按数量精确唤醒 N 个工作线程（目前只区分"一个/全部"）               | 大批量入队时的无效唤醒进一步减少              |   中   |
| 入队路径的待处理计数与唤醒字是两次 `seq_cst` 原子操作，可合并为一次          | 每次入队省约 7 ns，`yield` 链边际成本降约 15% |   低   |
| 定时器到期前在 worker 中加入与 `thread_pool::timer_scheduler` 相同的自旋守时 | `sleep()` 额外偏差 130–180 µs 可降到 10 µs 级 |   低   |
| Windows (MSVC Release) 数据采集                                              | 补齐跨平台对比                                |   低   |

## 总结

NexusForce `virtual_thread` 在 Linux (Clang 20) 下的关键指标：

- **内联任务 43.7 ns**（裸协程下限 10.6 ns），比每任务建线程快约 **370×**
- **一次 `yield` 往返 3.07–4.32 µs**，与手写互斥池同量级；协程自身挂起/恢复仅 **38 ns**
- **提交吞吐约 5M tasks/s**（8 生产者），计算扩展 8 worker 86%、16 worker 73%（11.6× 加速）
- **`co_await` 子任务 153 ns/次**，扇出后摊薄到 0.63 µs/子任务（含跨核唤醒）
- **定时挂起额外偏差 130–180 µs**，200 ms 目标相对偏差 0.17%
- **空闲 worker 0.046% 单核**，不随 worker 数增长

## 场景推荐

- **大量短协程 + 少量阻塞等待**：内联执行路径 43.7 ns/任务，适合把回调拆成协程
- **I/O 挂起型并发**：单次挂起恢复 38 ns，远低于一次线程切换；配合 `sleep()` 做超时控制
- **需要限制在固定 worker 数的 CPU 负载**：任务体先 `yield` 再计算，8 worker 内可拿到 86% 扩展率
- **多生产者投递**：无锁队列让 8 生产者的提交速率达到约 5M tasks/s
- **不适用**：单线程严格串行的等待型负载（worker 越多单任务反而越慢）；1 ms 级精确定时（见定时精度一节）
