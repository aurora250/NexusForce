# NeForce RB Tree 性能评估

> 比较对象: `neforce::set` / `neforce::map`（底层 `neforce::rb_tree`）与 `std::set` / `std::map`
> 测试条目: 插入、带提示插入、原地构造、查找命中、查找未命中、按 key 删除、全量遍历、`count`、`lower_bound`、`equal_range`、拷贝构造，规模 1K / 32K / 256K / 1M；另有一组 `map` 用例
> 单位: **ns/op（单次操作耗时，越小越好）**；比值列 `<1` 表示 NeForce 更快，`>1` 表示标准库更快

---

## Linux

> 测试平台: i9-13980HX (8 P-core + 16 E-core = 32 逻辑 CPU), Linux 7.0.0-42, Clang 20 Release (`-mavx2`, 生效优化级别 `-O2`)，`NEXUSFORCE_USING_MEMORY_POOL=ON`
> 测量方法: `taskset -c 2` 绑定 P-core，`--benchmark_repetitions=3`，3 个独立进程取各条目最小值；两种实现分别编译在独立翻译单元中，避免同一 TU 内因内联压力不同造成的偏差
> 元素类型: 键为固定种子的确定性伪随机 `int`（同一次运行内两种容器使用完全相同键序），未命中查找使用负数键（必然不存在于树中）

### 插入性能（`insert`，随机键）

| 规模 | neforce | std | nf/std |
|-----:|---:|---:|--------:|
| 1024 |   16.302 ns |   25.532 ns |  0.638× |
| 32768 |   78.564 ns |  100.715 ns |  0.780× |
| 262144 |  153.280 ns |  173.126 ns |  0.885× |
| 1048576 |  304.964 ns |  358.122 ns |  0.852× |

- 1K 为 0.64×（每节点一次分配占主导），32K / 256K / 1M 为 0.78× / 0.89× / 0.85×，大表由节点访存主导
- 红黑树每插入一个节点即分配一次，分配器单次成本在小表下直接体现

## 架构特性矩阵

| 特性          | neforce::rb_tree                         | std::set / std::map (libstdc++)  |
|---------------|:----------------------------------------:|:--------------------------------:|
| 平衡策略      | 红黑树（Guibas & Sedgewick）             | 红黑树                           |
| 节点结构      | 左/右/父指针 + 颜色位，头节点作 `end()` 哨兵 | 左/右/父指针 + 颜色位            |
| 重平衡        | 插入最多 2 次旋转、删除最多 3 次旋转     | 同源算法                         |
| `find`        | 单次下界搜索 + 等值比较，命中即返回      | 单次下界搜索 + 等值比较          |
| `count`       | 唯一键容器复用 `find` 返回 0/1；多键容器一次下界 + 后继扫描 | 唯一容器复用 find，多键容器区间计数 |
| `equal_range` | 下界 + 上界两次搜索                      | 下界 + 上界两次搜索              |
| 拷贝构造      | 递归复制（O(n)）                         | 递归复制（O(n)）                 |
| 节点分配      | `neforce::allocator` → 内存池            | `std::allocator` → `operator new` |
| 迭代器        | 节点指针 + 容器指针（双向）              | 节点指针（双向）                 |

## 场景推荐

| 场景                     | 推荐实现                        | 原因                                   |
|--------------------------|---------------------------------|----------------------------------------|
| 范围 / 等值区间查询      | `neforce::set` / `neforce::map` | `equal_range` 快 1.5 ~ 1.6×，`lower_bound`（32K 以上）快 1.0 ~ 1.2× |
| 未命中查找为主           | `neforce::set`                  | 快 1.1 ~ 1.2×                          |
| 计数（`count`）          | 两者等价                        | 0.74 ~ 1.03×                           |
| 遍历                     | 两者等价（32K 以上）            | 0.95 ~ 1.00×；1K 小表快慢视实现而定    |
| 高频插入 / 删除          | 两者等价（1.0 ~ 1.3×）          | 均为每节点一次分配                     |

## 总结

对 56 个可比条目（14 个用例 × 4 个规模）做 `nf/std` 比值，几何均值 **0.78×**：

- **领先 41 项**、**持平 12 项**（0.95 ~ 1.05×）、**落后 3 项**
- 领先集中在有序查询与批量构建：`equal_range` 0.51 ~ 0.68×、`find`（32K 以上）0.73 ~ 0.94×、未命中查找 0.68 ~ 0.97×、`lower_bound`（32K 以上）0.85 ~ 0.97×、`count`（32K 以上）0.60 ~ 0.91×
- 仅剩 3 项落后：1M 带提示插入 1.30×（计时区间含 1M 节点的整表清理与重建）、1K `lower_bound` 1.83× 与 1K `find` 1.16×（二者走同一条下界路径，同一份代码在同一 TU 内产出不同内联形态）
- 插入 / 原地构造 / 删除 / 拷贝因节点块缓存而全面领先：1K 插入 0.64×、原地构造 0.49×、拷贝 0.40×、删除 0.85×
- 遍历（0.95 ~ 1.02×）与删除（0.85 ~ 0.97×）与 `libstdc++` 持平或更优：节点块缓存让节点按块连续分布

## 可优化方向

| 方向                                                                | 预期收益                        | 复杂度 |
|---------------------------------------------------------------------|---------------------------------|:------:|
| 1K 下 `lower_bound` 1.83× / `find` 1.16×：两者共用同一条下界路径却在同一 TU 内产出不同形态，隔离编译时反超 `std`，需稳定其内联形态 | 1K 两项收敛到 1.0× 以内 |   低   |
| 1M 提示插入 1.30×：计时区间含整表清理与节点块重建 | 该用例收敛到 1.0 ~ 1.1× |   中   |
