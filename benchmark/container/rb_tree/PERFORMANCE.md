# NeForce RB Tree 性能评估

> 比较对象: `neforce::set` / `neforce::map`（底层 `neforce::rb_tree`）与 `std::set` / `std::map`
> 测试条目: 插入、带提示插入、原地构造、查找命中、查找未命中、按 key 删除、全量遍历、`count`、`lower_bound`、`equal_range`、拷贝构造，规模 1K / 32K / 256K / 1M；另有一组 `map` 用例
> 单位: **ns/op（单次操作耗时，越小越好）**；比值列 `<1` 表示 NeForce 更快，`>1` 表示标准库更快

---

## Linux

> 测试平台: i9-13980HX (8 P-core + 16 E-core = 32 逻辑 CPU), Linux 7.0.0-42, Clang 20 Release (`-mavx2`, 生效优化级别 `-O2`)，`NEXUSFORCE_USING_MEMORY_POOL=ON`
> 测量方法: `taskset -c 2` 绑定 P-core，`--benchmark_repetitions=3`，3 个独立进程取各条目最小值
> 元素类型: 键为固定种子的确定性伪随机 `int`（同一次运行内两种容器使用完全相同键序），未命中查找使用负数键（必然不存在于树中）

### 插入性能（`insert`，随机键）

| 规模 | neforce | std | nf/std |
|-----:|---:|---:|--------:|
| 1024 |   33.140 ns |   25.521 ns |  1.299× |
| 32768 |  105.472 ns |  100.307 ns |  1.051× |
| 262144 |  181.936 ns |  175.610 ns |  1.036× |
| 1048576 |  327.261 ns |  370.013 ns |  0.884× |

- 1K 为 1.30×（每节点一次分配占主导），32K / 256K / 1M 为 1.05× / 1.04× / 0.88×，大表由节点访存主导
- 红黑树每插入一个节点即分配一次，分配器单次成本在小表下直接体现

## 总结

对 56 个可比条目（14 个用例 × 4 个规模）做 `nf/std` 比值，几何均值 **1.02×**：

- **领先 19 项**、**持平 19 项**（0.95 ~ 1.05×）、**落后 18 项**
- 领先集中在有序查询：`equal_range` 0.61 ~ 1.06×、`count` 0.74 ~ 1.03×、未命中查找 0.85 ~ 0.94×、1M 规模的 `find` 0.72 ~ 0.77×
- 落后集中在每节点分配的用例（1M 带提示插入 1.81×、拷贝构造 1.25×）与 1K 小表的热路径（`lower_bound` 1.84×、遍历 1.33×）
- 遍历、删除、计数在中大规模与 `libstdc++` 同量级，树的形态与节点布局一致

## 可优化方向

| 方向                                                                | 预期收益                        | 复杂度 |
|---------------------------------------------------------------------|---------------------------------|:------:|
| 1K 小表的比较热路径（`lower_bound` 1.84×、`find` 1.32×、遍历 1.33×） | 小表场景收敛到 1.0× |   中   |
| 每节点分配成本（插入 / 拷贝的 1M 档 1.81× / 1.25×） | 与分配器优化联动，收敛到 1.0 ~ 1.1× |   中   |
| 带提示插入的提示校验与分配路径合并                                  | 1M 规模提示插入由 1.81× 收敛 |   低   |
| 节点分配批量预取（一次 span 内放置多个节点）                        | 插入/删除/拷贝的每节点分配成本下降 |   高   |
