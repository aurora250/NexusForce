# NexusForce 开发规范

本文档面向 NexusForce 的所有贡献者，定义项目的**设计哲学**与**开发思维规范**。  
关于代码格式（缩进、空格、换行等），请遵循项目根目录的 `.clang-format` 配置。

> **核心目标**：功能健全、风格统一、可读性强、社区共建、跨平台兼容。

---

## 一、设计哲学

### 1.1 从正确到性能

- 代码必须清晰可测。
- 性能优化必须基于 profiling 数据（如 perf、Valgrind、Google Benchmark）。
- 热路径、已知瓶颈可设计高性能方案，须在注释中说明。

### 1.2 明确机制

- 避免晦涩的模板元编程、宏魔法、复杂运算符重载。
- 优先使用 `constexpr`、`static_assert`、`if constexpr` 等清晰机制。

### 1.3 资源安全

- **尽量不使用裸 `new` / `delete`**。
- 尽量使用 `unique_ptr`、`shared_ptr`、`optional`、`variant`、`memory_view`、`string_view`。
- 所有资源（锁、文件、内存、socket、数据库连接）必须提供 RAII 类型进行管理。

### 1.4 统一异常

NexusForce **默认启用异常**，错误处理遵循：

- 构造函数失败、真正异常情况 → 抛出异常。
- 可恢复错误 → 返回 `optional`、`expected`或 `bool`。
- **禁止**：错误码 + 输出参数混用、不检查返回码、吞掉异常。

## 二、架构与接口设计规范

### 2.1 模块组织

每个模块（如 `async`、`container`、`memory`）应满足：

- 独立头文件目录 `include/NexusForce/<Module>/`
- 对应源文件目录 `src/<Module>/`
- 模块间依赖最小化，避免循环依赖。

### 2.2 接口紧凑

- 每个类/函数只做一件事（单一职责）。
- 优先写命名空间下的自由函数，而非将所有逻辑塞入类成员。

### 2.3 不变式

- 成员函数在不修改对象状态时必须 `const`。
- 小对象参数（小于等于16字节）用值传递，大对象用 `const T&`
- 类必须定义**不变式**（invariant），在构造后成立，并在公有方法前后保持。

### 2.4 生命周期

- 明确区分：
  - 拥有资源的对象（`unique_ptr`）
  - 只观察的对象（`string_view`）
- 避免循环引用：使用 `weak_ptr` 或重构设计。
- 移动语义正确实现：`= default` 或成员逐个移动。

---

## 三、并发与线程模型

### 3.2 锁与数据竞争

- 共享数据 → 使用 `mutex` + `lock` / `unique_lock`。
- 临界数据必须是 `atomic` 或受锁保护，**禁止猜测无竞争**。

### 3.3 异步与阻塞明确标注

- 函数若可能阻塞或执行耗时操作，名称中加 `Blocking` 后缀（如 `ReadBlocking`）。
- 异步函数返回 `Future<T>` 或接受回调，名称加 `Async` 后缀。

### 3.4 线程安全承诺

每个公有类型须在文档中明确说明：
- **线程安全**：可被多线程并发调用。
- **线程兼容**：外部同步时安全。
- **线程不安全**：仅限单线程使用。

## 四、可维护性与演进规范

### 4.1 版本兼容性策略

NexusForce 遵循**语义化版本**：`MAJOR.MINOR.PATCH`

- **MAJOR**：破坏 API/ABI 兼容性
- **MINOR**：新增功能，向后兼容
- **PATCH**：Bug 修复，向后兼容

破坏性变更流程：
1. 使用 `[[deprecated("message, will be removed in vX.Y")]]` 标记废弃。
2. 保留至少两个 MINOR 版本。
3. 更新文档和迁移指南。

### 4.2 内部实现保护

- 所有不对外公开的实现放入 `inner` 命名空间。
- `inner` 中的内容不保证 API 稳定性，patch 版本可变更。

### 4.3 依赖管理

- 依赖通过 **vcpkg** 管理。
- 新增依赖必须在 PR 中说明理由，并更新 README 和 CMakeLists。
- 避免传递不必要的依赖。

### 4.4 文档义务

- 每个公有头文件必须有模块级注释（说明模块目的、使用示例）。
- 每个公有类、函数、枚举、模板必须有 Doxygen 风格注释，至少包含：
  - `@brief`：简要描述
  - `@param`：参数说明
  - `@return`：返回值说明
- 复杂算法（如红黑树）须附论文链接或算法说明注释。

## 五、测试与质量门禁

### 5.1 测试要求

- 每个新特性或 Bug 修复必须伴随测试。
- 测试框架：**GoogleTest**。
- 测试类型：
  - 单元测试（`test/unit/`）
  - 集成测试（`test/integration/`）
  - 并发压力测试（`test/stress/`，针对无锁队列、线程池等）

### 5.2 覆盖率要求

- 核心模块行覆盖率 ≥ 90%
- 全项目行覆盖率 ≥ 70%

### 5.3 CI 强制检查

每个 PR 必须通过：

- `.clang-format` 格式化检查
- **Clang-Tidy**
- **CodeQL** 安全分析
- **Valgrind** 内存泄漏检测
- 所有测试在 Debug 和 Release 模式下通过

## 六、开发流程与协作规范

### 6.1 Pull Request 要求

**标题格式**：`[模块名] 简短描述`  
示例：`[container] 修复红黑树旋转时的内存泄漏`

**PR 描述模板**：

```markdown
## 设计决策
（说明为什么这样实现，替代方案有哪些）

## 性能影响
（对性能有提升/下降？附 profiling 数据）

## 测试情况
- [ ] 单元测试通过
- [ ] 集成测试通过
- [ ] 无内存泄漏
- [ ] 覆盖率达标

## 兼容性
- [ ] 不破坏现有 API
- [ ] 若破坏，已提供迁移指南
```

**PR 大小限制**：≤ 400 行变更（超出必须拆分，除非有充分理由）。

### 6.2 代码审查关注点

审查者重点检查：
- 设计是否合理、是否符合本规范
- 不变式是否保持
- 错误处理是否完整
- 并发安全性
- 资源泄漏
- 测试覆盖是否充分

**禁止**：因个人风格偏好拒绝 PR（交给 `.clang-format` 和 Clang-Tidy）。

### 6.3 Git 提交规范

遵循 **Conventional Commits**：

```
<type>(<scope>): <subject>

[optional body]

[optional footer]
```

**type** 类型：
- `feat`：新功能
- `fix`：Bug 修复
- `docs`：文档变更
- `style`：格式化（不影响代码运行）
- `refactor`：重构
- `perf`：性能优化
- `test`：添加测试
- `chore`：构建/工具变更

示例：  
`feat(network): 添加 WebSocket 自动重连机制`  
`fix(async): 修复线程池任务窃取时的死锁`

### 6.4 禁止事项

- ❌ 注释掉的代码块
- ❌ 未使用的变量、函数、include
- ❌ 在头文件中使用 `using namespace neforce;` 或任何全局 using 指令
- ❌ 忽略编译器警告（除非有合理理由）

## 七、特殊模块规范

### 7.1 并发模块（async）

- 无锁数据结构（`无锁队列`、`危险指针`）必须附带**形式化正确性论证**或**已知论文引用**。
- 线程池的任务窃取算法须有性能测试证明其优于简单队列。

### 7.2 加密模块（encrypt）

- **严禁自己发明或修改加密算法**。所有实现必须基于标准文档（FIPS / RFC）。
- 加密函数必须恒定时间执行，防止时序攻击。

### 7.3 内存管理（memory）

- 自定义分配器必须通过项目统一的内存跟踪接口，便于调试。
- 禁止在析构函数中抛出异常。
- `compressed_pair` 等优化技巧必须有注释说明其必要性。

### 7.4 跨平台兼容性

避免使用平台特有 API，除非在 
`#ifdef NEFORCE_PLATFORM_WINDOWS` / `#ifdef NEFORCE_PLATFORM_LINUX`
中隔离，并提供跨平台抽象。

## 八、社区共建原则

### 8.1 欢迎新手

- 所有 `TODO` 标记的任务优先分配给首次贡献者。
- 代码审查应**建设性**：指出问题时同时给出改进建议或示例。

### 8.2 决策机制

- 设计争议：提交 **RFC 文档**（`docs/rfc/`）讨论，至少 72 小时反馈期。
- 核心模块变更：需至少一位项目维护者批准。

### 8.3 致谢

所有贡献者将列入 [`CONTRIBUTORS.md`](CONTRIBUTORS.md)。  
重大设计或性能突破将在 `CHANGELOG.md` 中特别致谢。

---

## 九、规范更新流程

本规范随项目演进更新。任何贡献者可以：

1. 在 `docs/DEVELOPMENT.md` 上提交 PR 修改建议。
2. 在 PR 描述中说明修改理由和影响范围。
3. 至少两位维护者批准后合并。
